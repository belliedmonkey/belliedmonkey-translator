品牌 token 与字体

色板沿用，未新增色相

给定七个品牌色不变。派生色一律用 oklch() 从既有色推出，规则是「只沿 OKLch L 轴加深 0.06–0.12」，因此每个交互态的前景/背景对比度都只能变好，不可能变差 —— 这条比逐个手调 hex 更适合进门禁。

层级与尺寸：每一块为什么在这里

iPhone 竖屏 390×844 为基准

这一屏只回答一个问题：现在能干什么。所有与「已经做完的事」有关的内容（系统翻译接管、词库总量统计）都必须让位给还没开始的事。

块级iOS 尺寸理由
顶栏H244pt · 高 52只承载身份与账号。账号行（邮箱 + 设置/退出）从独立 48pt 横带收进 44×44 圆形键 —— 它是全局动作，不该占首屏版面
引擎状态行H3高 32 · 命中 44唯一的前置条件说明位。就位时是低对比绿摘要（保证），缺失时原地变成可点 chip（待办）。放在它前面是因为待办必须前置 —— 现状把它扔在 y=1275 的页脚，用户要滚 431pt 才看到
实时字幕卡H1高 236 · 按钮 50本页主角。构成：32pt 图标 + 20pt 标题 + 就绪标 + 13.5pt 两行说明 + 46pt 波形带 + 50pt 实心按钮。波形带既是说明也是进行态的实时表面，不是装饰
实时听译卡H1高 236 · 按钮 50与字幕等高同权。只有卡内视觉不同（波形 vs A·B 译文条）。两个实心按钮对应两个不同动作，不违反「一个动作一枚主 CTA」
复习条H3高 76 · 按钮 40裁定 4 要求「看得见、一眼能开始」。76pt 是同时满足可点与不抢戏的最小值；按钮用淡色档而不是实心，主动降一档
文档分区 + 行H420 + 56异步任务，落在折叠线附近。列表行形态，不给卡片。独立于「听」分区
系统翻译行H456 · 起 y≈845就位后才成立的事实陈述。轻：真实系统图标 + 一行主副文案 + chevron，点了才展开说明

三档，不允许第四档
档外观用途hoverpress
实心 filled底 --btn / 字 #fff仅两个：开始实时字幕、开始听译--btn-hover（L −0.071）--btn-press（L −0.116）
淡色 tinted底 --bg / 字 --fg开始复习、去配置（在面板内）换面为 --surface + 边框 --muted边框 --muted
描边 ghost底 --surface / 字 --fg取消、停止、结束并保存底 --bg + 边框 --muted边框 --muted
文字 plain字 --terra-ink查看统计、字幕浮窗底 --terra-wash同上
禁止的四件事　① hover 时把文字变 --muted 或任何更接近背景的颜色。② 同屏出现两枚以上同档实心按钮指向同一动作。③ 用 --terra 纯色做 13pt 以下的文字（3.03:1 不够）。④ 给可点元素留 <44pt 命中区而不标注外扩。
态规则
hover只动背景 L（±0.06–0.12）或边框 / 阴影 / 位移。前景永不变淡
active / pressed同向再深一档；不允许出现比默认态更低的对比度
focus-visible2.5px --terra-ink 描边 + 2px offset，落在任何可 Tab 到的元素上
disabled唯一允许降低对比度的状态。底 --line，字仍需 ≥3:1；本设计中不使用 disabled —— 缺引擎时按钮变为可点的去配置而不是变灰
VoiceOver每张卡的按钮独立朗读（「开始实时字幕，按钮」），缺失 chip 带 aria-label 指明目标页

引擎状态矩阵

裁定 2 的落地表

「登录完就该所有引擎都配好」是目标态。下表是这个目标态失效时各能力的真实退化路径 —— 没有一条路径是纯文本告警。

缺失 / 异常状态行实时字幕卡实时听译卡系统翻译段
全部就位（默认）绿摘要「已就位」，非交互就绪 + 实心「开始」就绪 + 实心「开始」渲染一行
朗读缺失朗读 · 去配置 › chip（terra）不受影响，仍可开始按钮变「朗读未选声音 · 先选一个 ›」不渲染
语音转写缺失语音转写 · 去配置 › chip按钮变「先选一个转写引擎 ›」按钮变同左不渲染
翻译引擎缺失翻译 · 去配置 › chip按钮变「先选翻译引擎 ›」按钮变同左不渲染

为什么用 terra 而不是红色标注缺失　缺一个引擎是待办，红色会让用户以为出故障了、进而放弃这个功能。红色留给「你按了按钮但它失败了」—— 那种情况才需要 alarming。同时这也顺手解决了现状页底部红字滥用的问题。

iOS 与 macOS 的四处刻意差异

同层级，不同落地
项iPhone 390×844Mac 1440×900为什么不统一
账号与设置 / 退出顶栏 44×44 圆形键 → 底部面板侧栏底部常驻宽屏有侧栏这件事本身就是答案：不该再让账号占用主区版面
权限呈现系统权限弹窗（原生层呈现，界面内不重绘）macOS TCC 提示由系统承接；界面内只有准备态检查表WKWebView 无法自绘权限弹窗。两端各写一套文案必然漂移，规约里必须写死由原生层承接
系统翻译的落点主区列表行（折叠线以下）侧栏项宽屏上「轻」的最省事落地：侧栏本来就是目的地列表，不需要在主区再造一块
主按钮满宽 50pt左对齐定宽 40ptHIG：macOS 的 prominent 按钮是行内元素，满宽按钮在桌面端读起来像网页表单

待确认与外部依赖

确认后才能锁进交互规约
本规格未覆盖的两类问题
① 取音路径的定义。两张卡的说明文案（「这台设备正在播放的声音」与「面对面的说话」）已经把取音对象写死了，但 iOS 上「设备播放声音」与「麦克风拾音 + 回声消除」是两条完全不同的实现路径，会带来不同的权限文案与失败态。规约必须先写死这一条，否则两张卡的文案会在实现期互相矛盾。
② 「实时字幕」的浮窗 / 锁屏形态。本稿按「浮窗开关只在进行中态」处理（见评审画布待拍板第 3 条）。若产品决定把它提为首页常驻项，H1 卡的高度预算与 J01 都要重算。
