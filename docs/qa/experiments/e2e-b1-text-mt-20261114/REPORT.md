# 端到端基线 B1：文本翻译两条件对照（第一轮）

时间：2026-11-14 13:12–13:52 CST（UTC+8）。授权：用户批准 B1 预算。
结论：**瓶颈在上游识别，不在翻译。** 金标文本输入的译文 36/36 全维通过；换成产品 ASR 输出当输入，只有 15/35 通过，意义保全掉 36.6 个点。

这是探索性组件对照，**不是产品分、不是排名、不是验收**。判审没有人工金标，TPR/TNR 未知。

## 1. 口径

同一 36 条冻结样本，两个输入条件：

| 条件 | 输入 | 回答的问题 |
|---|---|---|
| A | 参考转写（FLEURS / ASCEND 金标） | 纯翻译质量 |
| B | 产品 SA 假设（`aef9aa8f` 冻结文件） | 真实链路质量 |

- 翻译走产品的真实系统提示词（`extension/content/translation-api.js` 的 `buildSystemPrompt`，脚本启动时逐行核对仓库原文），模型为产品钉住的 `qwen3.7-plus`，`temperature=0`，端点为 QwenCloud 国际站 compatible-mode
- 方向：`en_us` → `zh-CN`，`cmn_hans_cn` 与 `ascend` → `en`
- 双评委盲评：`openai/gpt-4.1-mini` 与 `qwen/qwen3-235b-a22b-2507`，独立、互不可见
- 判定基准是**金标转写**，不是条件里的输入。B 条件额外把 ASR 文本给评委，并写明「继承的识别错误算它的」
- 七个维度二元判定：意义、实体与数字、否定、遗漏、幻觉、术语、流畅

### 第一轮判定作废的原因

初版把 B 条件的 ASR 文本当成「源」交给评委，量到的是「对错源的忠实度」，不是端到端语义损失。那一轮 A/B 只差 18.1 个点，方向对、口径错。改以金标为准后重判，即本文正式数字。两轮判定账目都留着，见第 6 节。

## 3. 归因结论

- **翻译不是瓶颈。** 干净输入下七个维度全过，包括术语与否定。
- **识别是瓶颈。** 同一批译文，只把输入从金标换成产品 ASR 输出，意义保全从 100% 掉到 63.4%。
- **译文在输入坏掉时不会崩成病句**：流畅 100%、否定 100%。模型会把听到的碎片补成通顺句子——这解释了为什么幻觉（81.7%）和遗漏（87.3%）同时掉：补得越顺，编得越多。
- 混语与英文子集比中文子集更差，与 SA 的混语 MER 24/42、英文 WER 36/363 方向一致。

## 4. 这套判审还不能当验收

- 无人审金标，`semanticHumanReviewCount` 仍是 0，judge 的 TPR/TNR 未知
- 两评委在「七维是否全过」上一致 52、分歧 19（分歧率 27%）。单评委数字会误导
- **A 条件 100% 饱和**：说明这 36 条对翻译维度太容易，量不出翻译的上限差异。要继续量翻译，得换更硬的样本（长句、专名、数字密集、术语域），不是加评委
