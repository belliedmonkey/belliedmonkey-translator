# 端到端基线 B1：文本翻译两条件对照（第一轮，产品口径）

时间：2026-11-14 13:12 CST 起，2026-11-15 07:47 CST 完成产品口径重跑。授权：用户批准 B1 预算。
结论：**瓶颈在上游识别，不在翻译。** 金标文本输入的译文 36/36 全维通过；换成产品 ASR 输出当输入，只有 40/72 评委次全维通过，意义保全 58.3%。

这是探索性组件对照，**不是产品分、不是排名、不是验收**。判审没有人工金标，TPR/TNR 未知。

## 0. 更正声明（先读这段）

本记录的第一版把「78% 的 completion token 是推理 token」写成了产品的成本与延迟问题。**那是错的，本记录的 harness 漏发了产品必发的参数。**

- 产品对 `qwen3.7-plus` 显式发送 `enable_thinking: false`：`build/model-params.config.js` 的 `qwencloud` 行有 `reasoning: { enable_thinking: false }`，`extension/content/request-shape.js` 的 `applyReasoning` 把它**平铺到请求体顶层**。同文件还记着 2026-11-10 的 A/B：「不钉任何参数时 200 但会思考（218 completion tok）；显式 `enable_thinking:false` 后 200 / completion 1 tok / reasoning 0，译文长度不变」。
- 第一版请求体里只有 `model` / `temperature` / `messages`，没有这个字段。
- 现已改成从 `providers.gen.js` 解析 `qwencloud` 行的 `reasoning` 片段、断言它等于 `{enable_thinking:false}`、按产品同样方式顶层合并。**本记录的 `out/` 是产品口径数据**，第一版的思考开着的数据只保留汇总在 `ledger/thinking-contrast.json`。

这一项修正不改变结论，反而让它更硬：关掉思考后 B 条件更差。

## 1. 口径

同一 36 条冻结样本，两个输入条件：

| 条件 | 输入 | 回答的问题 |
|---|---|---|
| A | 参考转写（FLEURS / ASCEND 金标） | 纯翻译质量 |
| B | 产品 SA 假设（`aef9aa8f` 冻结文件） | 真实链路质量 |

- 翻译走产品的真实系统提示词（`extension/content/translation-api.js` 的 `buildSystemPrompt`，脚本启动时逐行核对仓库原文）、产品钉住的 `qwen3.7-plus`、产品的 `reasoning` 片段，`temperature=0`，端点为 QwenCloud 国际站 compatible-mode
- 方向：`en_us` → `zh-CN`，`cmn_hans_cn` 与 `ascend` → `en`
- 双评委盲评：`openai/gpt-4.1-mini` 与 `qwen/qwen3-235b-a22b-2507`，独立、互不可见
- 判定基准是**金标转写**。B 条件额外把 ASR 文本给评委，并写明「继承的识别错误算它的」
- 七个维度二元判定：意义、实体与数字、否定、遗漏、幻觉、术语、流畅

**20 / 36 条「A 过、B 不过」**，这 20 条是识别误差传导到译文的直接损失。

按子集（B 条件，任一评委判有缺陷的条目）：ASCEND 混语 4/6（67%）、`en_us` 9/15（60%）、`cmn_hans_cn` 7/15（47%）。

缺陷维度计数（按评委次）：意义 26、实体与数字 17、幻觉 13、遗漏 9、术语 8。

## 3. 归因结论

- **翻译不是瓶颈。** 干净输入下七个维度全过，包括术语与否定。
- **识别是瓶颈。** 只把输入从金标换成产品 ASR 输出，意义保全从 100% 掉到 58.3%。
- **坏输入不会变成病句，会变成编造。** 否定与流畅在 B 下仍是 100%，但幻觉掉到 73.6%、遗漏掉到 79.2%。模型把听到的碎片补成通顺句子，补得越顺编得越多。修 ASR 的收益会直接体现为幻觉与遗漏下降，不是流畅度上升。
- 混语与英文子集比中文子集更差，与 SA 的混语 MER 24/42、英文 WER 36/363 方向一致。

## 4. 思考开关的真实代价（产品口径之外的一次对照）

同一三条中文样本，只改 `reasoning` 片段，单次调用实测：

| 配置 | 时延 | completion tok | reasoning tok |
|---|---|---|---|
| 不发参数（第一版的错误口径） | 10714 / 8168 / 16264 ms | 550 / 455 / 861 | 514 / 430 / 798 |
| `enable_thinking:false`（产品口径） | 1786 / 1460 / 1994 ms | 30 / 24 / 67 | 0 / 0 / 0 |

整轮 72 次：思考开着 46720 completion tok（44682 推理），产品口径 1805 completion tok、0 推理。**约 26 倍 token、约 6 倍时延。**

思考开着时 B 条件略好（意义 63.4% vs 58.3%，幻觉 81.7% vs 73.6%），A 条件完全一致。也就是：思考买回了坏输入上约 5 个点的语义，代价是 26 倍 token——产品当前的取舍是对的，这条不需要改。

## 5. 这套判审还不能当验收

- 无人审金标，`semanticHumanReviewCount` 仍是 0，judge 的 TPR/TNR 未知
- 两评委在「七维是否全过」上一致 51、分歧 21（分歧率 29%）。单评委数字会误导
- **A 条件 100% 饱和**：这 36 条对翻译维度太容易，量不出翻译上限。要量翻译得换更硬的样本（长句、专名、数字密集、术语域），不是加评委
